# 中间版本总结（2026-08-01）

> 定位：站在 VISION v2.1 + framework-design v2.1 回看当前代码（v0.1.0 → 架构转型期）。
> 回答三个问题：思路对不对？基础打牢了没有？开发方向有没有出错？

---

## 一、这个中间版本是什么

一句话：**一个能跑通"事件驱动 + 常驻进程 + Web 面板"骨架的单体 ReAct 编码代理**。
25 个源文件、5 个工具、3 个进程入口（index / subagent-cli / actor）、2 种执行模式（oneshot 一次性 / actor 常驻）、1 个 Web Dashboard。

演进路径：单次 ReAct（07-13）→ chat 多轮（07-14）→ daemon 事件循环（07-29）→ Actor 常驻 + talk + Web 面板（07-29/30）。

---

## 二、思路对不对：✅ 对——演进路径与愿景重合

这不是事后诸葛：**代码的演进顺序（单次 → 多轮 → 事件驱动 → 常驻进程 → 多前端）恰好就是愿景地基的建造顺序**。07-29 那批提交（Sink 事件总线 / Web Dashboard / Actor 模型 / talk）在愿景被写清楚之前，已经本能地走向了 framework-design 的模块结构。

| 愿景机制 | 代码里的种子 | 成熟度 |
|---|---|---|
| 服务协议通道 | `actor.ts` stdin/stdout JSONL 循环 + `actor-handle.ts` pending-promise | ⚠️ 通道模式对，协议词表乱（见 §三） |
| 全局状态模型 | `agent-registry.ts` L1/L2/L3 分层 | ✅ 骨架正确 |
| 事件入口 | `inbox.ts` | ✅ |
| 事件总线 | `sink.ts` MultiSink | ⚠️ 只做 UI 广播，无分级无路由 |
| 集群循环 | `orchestrator.ts` daemon 模式 | ⚠️ 事件循环对，但 LLM 当调度器（见 §三） |
| 通知出口 | `server.ts` WebSocket | ✅ 种子 |
| 交互型节点 | `talk` 多轮对话 | ✅ 雏形 |
| 一次性任务 | `subagent-cli.ts` + worktree 隔离 | ✅ 保留 |

**结论：没有走错的大弯。** 中间版本证明了两件事：骨架能跑通（daemon + actor + talk + web 是工作的），愿景所需的机制在代码里都有对应种子。差距是"从种子到机制"的工程化，不是推倒重来。

---

## 三、基础打牢了没有：工程基础 ✅ / 架构基础 ⚠️

### 打牢的（工程基础，值得保留）

1. **工程卫生**：TypeScript strict、biome、husky、lint-staged、CI、CodeQL、`.gitattributes` LF 行尾——这套体系是完整的。
2. **LLM 层成熟**（`llm.ts`）：指数退避重试、429/5xx/网络错误分类、AbortSignal 超时透传、`reasoning_content` 透传——一个生产级 LLM 客户端该有的都有。
3. **子 Agent 抗崩**（`dispatcher.ts` SubAgent）：maxTokens 翻倍重试（截断检测，line 380-387）、连续空结果提前终止（line 419-434）、总时长限制、LLM 超时 abort——这些是踩过坑才写得出的防护。
4. **Windows 兼容**（`tools.ts`）：Git Bash 探测、grep 降级链（git grep → PowerShell → 报错）——实打实的跨平台工程。
5. **Registry 三层状态**（`agent-registry.ts`）：L1 一行快照（不进上下文）/ L2 按需 peek / L3 完整对话——**这正是 StateStore 的分层骨架**，设计是对的。
6. **传输选型**：stdin/stdout JSONL + 文件 IPC + worktree——简单、可流式、跨进程，方向正确。

### 没打牢的（架构基础，下一阶段的改造点）

1. **协议三词表**（最大改造点）：`ActorInput/ActorOutput`（actor.ts）、`SinkEvent`（sink.ts）、`AgentEvent`（types.ts）互不相通。`dispatcher.ts:113-157` 的 onOutput 手工把 actor 消息翻译成 sink 事件再翻译成 inbox 事件——**每加一种事件类型要改三处**。这就是 framework-design §1 要统一的那个协议。
2. **LLM 当调度器**：`orchestrator.ts:175-216` 每批 agent_done 都跑一次完整 reactLoop 让 LLM 合成——调度中枢是 LLM 而不是纯代码。愿景明确要求"调度中枢纯代码、LLM 只在推理节点"。这不是错路，但 Phase 2 必须刻意换成 Flow 门控（第一个卸任点：agent_done 处理）。
3. **隐藏的 dispatch 控制器**：`tool-executor.ts:41-57` 从 LLM 参数现场拼 DispatchConfig（responseSchema 硬编码、max_rounds 固定 30、role 拼进 instructions）——dispatch 行为写死在代码里，违背"设计即服务"。行为应该来自服务契约/Flow，不是工具函数的现场拼接。
4. **无权限 enforcement**：`ToolExecutor` 不检查任何权限，`bash` 对任何子 agent/actor 裸奔（allowed_tools 默认含 bash）——愿景的"刹车片"（§9）缺失。
5. **无守护**：`actor-handle.ts:45-49` 进程退出只打日志——无心跳、无退避重启、无启动恢复。"7×24 常驻"尚未兑现。
6. **task/ask 上下文混杂**：`actor.ts:117-176` task 和 ask 共用 `state.messages`——任务执行污染交互记忆，反之亦然。交互上下文与任务上下文应分离（服务级记忆）。
7. **记忆是平面日志**：`memory.ts` 所有对话（含诊断 dump）追加进每日 JSONL——是日志不是记忆系统，无分层（服务级/事实库/用户模型）。
8. **新架构测试不足**：daemon 循环、actor 协议、dispatcher 异步、registry 分层——这些最危险的新代码缺少自动化测试（工作区的 `subagent-write-real*.test.ts`、`test_empty_rounds.ts` 是手工/实验性验证的痕迹）。

## 四、开发方向有没有出错

**没有需要推倒重来的弯。** 但有三个"习惯"需要在下一阶段刻意纠正，否则会越走越远：

| 习惯 | 现状 | 要换成 |
|---|---|---|
| LLM 编排一切 | 每批结果都过一遍 reactLoop | 纯代码事件分类 + Flow 门控，LLM 只在兜底 |
| 行为写死在工具里 | dispatch 控制器现场拼配置 | 行为来自服务契约 / Flow（设计即服务） |
| 事件类型三处手写映射 | dispatcher onOutput 翻译链 | 统一协议 + 契约 emits/consumes 声明 |

另外两个小问题：工作区有大量未提交的测试产物（`nul`、`output.json`、`file.md` 等），建议归档清理；`package.json` 的 test 脚本格式乱了（缩进错位）。

## 六、结论

1. **思路**：对。演进路径与愿景重合，愿景是对已有直觉的形式化；
2. **基础**：工程基础打牢了（类型/lint/CI/LLM 层/抗崩防护/分层状态），架构基础是"种子齐了但机制未成型"——协议统一、纯代码调度、权限、守护是欠的账；
3. **方向**：没有错弯，三个习惯需要刻意转换（LLM 卸任调度、行为从契约来、协议唯一）；
4. **中间版本的价值**：它把愿景里最难的假设（事件驱动 + 常驻进程 + 多前端能跑通）验证成了事实。下一步不是重做，是 framework-design Phase 1：**统一协议 → 服务契约 → Supervisor → 最小 Flow → 人装两个示例服务**。
